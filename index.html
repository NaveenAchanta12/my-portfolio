CodeTrail

Independent project · Browser-based learning & collaborative study

I built CodeTrail by SWOT & Study: a browser-based learning platform with executable Python practice, collaborative study rooms, Google sign-in and context-aware AI assistance.

Visit websiteGitHub repository
What I built

  • Controlled corrections. I checked source freshness and response completeness before applying generated code. Undo also checks for subsequent edits before restoring a previous version.
  • Adversarial regression tests. I maintain a documented 139-test regression suite, alongside focused checks for account isolation, stale writes, membership races, revoked grants and malformed image uploads.

Inside the implementation

CodeTrail by SWOT & Study combines a vanilla JavaScript interface with Cloudflare Workers, D1 / SQLite and context-aware AI assistance.

Execution isolation

Python runs in a dedicated Worker rather than on the interface thread. The browser can terminate a run without losing the surrounding learning workspace. The Java learning path uses editing and code downloads.

Optimistic concurrency

Progress writes include the expected revision. SQL updates only the matching account and revision, then advances the revision; conflicting requests receive the current state instead of silently overwriting it.

Authorization at write time

Shared-editor operations check the current room membership, enrollment, blocking state and edit grant. This addresses the gap between a user opening an editor and permissions changing before a later save.

Private-by-default collaboration

A learner's own study buffer starts private. Sharing a buffer and granting another member editing permission are separate operations, and revocation prevents old grants from reappearing after rejoining.

Google identity and sessions

Google OAuth / OpenID Connect uses the authorization-code flow with PKCE and ID-token verification. Expiring server-side sessions, secure cookies and revocation on logout keep identity separate from client-supplied data.

Server-side AI integration

The OpenAI Responses API powers contextual assistance using course material, editor code and console output. The design includes per-user and site-wide usage limits and a shared AI budget. Optional WebLLM inference remains a separate browser-based capability.

Safe editor integration

A proposal is bound to the lesson, language and code snapshot used to generate it. Incomplete replies and stale snapshots do not become editor changes; undo preserves edits made after an applied correction.

Regression coverage

The project documents 139 regression tests. Focused data-boundary suites exercise concurrent mutations, access revocation and invalid media without depending on live learner data.

Core engineering concepts

Worker isolation, WebAssembly integration, OAuth / OpenID Connect, session security, optimistic concurrency, backend authorization, contextual AI integration and regression testing.

Inside the implementation

Policy-centered data access

Server checks combine ownership, relationship status, field audiences and blocking. Interface visibility reflects these rules rather than defining access.

Concurrency at the database boundary

Reservation updates carry conditions that must still hold when SQL executes, backed by uniqueness constraints. A disabled interface button is not the final arbiter of who reserves a wish.

Audience-specific responses

Giver coordination and recipient views receive different information. The application can support planning without returning private reservation details to the recipient.

Authorized messaging and files

Message updates use polling with access checks. Media retrieval is also authorized, with private objects held separately from public presentation.

Controlled external input

Product import constrains retailer hostnames and redirects and bounds downloads. Manual entry keeps the workflow usable when extraction is unavailable.

Privacy-aware delivery

The responsive PWA supports installation, while authenticated personal content remains network-only rather than entering the offline cache.

Core engineering concepts

Relational modeling, backend authorization, concurrency control, audience-specific API responses, controlled URL fetching, private object storage and cache boundaries.

The agentic workflow
  1. Confirm the candidate context

    Use owner-scoped facts, résumé documents, preferences and verified answers.

  2. Discover and assess opportunities

    Create bounded search tasks, retain job evidence and evaluate fit against the selected criteria.

  3. Prepare reviewed content

    Bind wording, documents and answers to their source versions and surface missing information.

  4. Plan a browser action

    Turn a fresh page observation into a structured proposal.

  5. Validate before execution

    Check schema, policy, scope and current page state before the browser worker acts.

  6. Record and reconcile

    Persist progress and evidence; pause on uncertainty rather than blindly repeating a potentially completed action.
